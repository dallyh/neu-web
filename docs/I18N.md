# Internationalization

## Technology

Use `astro-intlayer` for user-interface translation.

The Astro integration currently provides Intlayer dictionary preparation, Vite integration, locale middleware, and localized page handling. In Astro components, `useIntlayer()` resolves a dictionary according to the active request locale, while `useLocale()` exposes the active/default/available locales.

## Responsibility boundary

### Intlayer owns

- navigation
- buttons
- headings that belong to application chrome
- form labels
- filter controls
- generic page labels
- error/empty states
- accessibility labels
- pagination
- theme/locale control labels

### MDX owns

- project titles
- project summaries
- project case-study prose
- blog titles
- blog descriptions
- blog article body
- localized editorial metadata

This rule prevents the same content from being represented in two translation systems.

## Configuration and dictionary

`astro.config.mjs` registers `intlayer()`. `intlayer.config.ts` configures `locales: ["en", "cs"]`, `defaultLocale: "en"`, and `routing: { mode: "prefix-all", enableProxy: false }`.

UI strings live in `src/i18n/site.content.ts`, whose dictionary key is `site`. Entries use `t({ en: ..., cs: ... })`; plural labels use Intlayer's `plural`. Astro components consume them with `useIntlayer("site")` and resolve the locale with `useLocale()`.

```astro
---
import { useIntlayer, useLocale } from "astro-intlayer";
const ui = useIntlayer("site");
const { locale } = useLocale();
---

<nav aria-label={ui.navigation}>...</nav>
```

## Locale-aware links

`src/lib/urls.ts`, `content.ts`, `tags.ts`, `privacy.ts`, and `open-graph/urls.ts` wrap Intlayer's `getLocalizedUrl()` for section, content, tag, policy, feed, and image URLs. Reuse those helpers instead of manually prepending locale prefixes. There is no separate translation map or `t.ts` helper.

## Locale switcher behavior

The root `/` route is an on-demand `GET` endpoint in `src/pages/index.ts` that returns an HTTP 302 response. Intlayer's `getLocaleFromRequest()` first checks the configured locale cookie, then negotiates `Accept-Language`, then falls back to `defaultLocale`. Responses use `Cache-Control: private, no-store` and vary by cookie and browser language. Intlayer's automatic routing proxy is disabled so the root route handles this consistently in development and production; explicitly localized URLs continue to determine the rendered language.

On a normal locale-switcher click, a small browser script calls the `setLocale` Astro Action before following the existing translated link. The action validates against the configured locales and uses Intlayer's storage helper to set its locale cookie for one year (`HttpOnly`, `SameSite=Lax`, and `Secure` over HTTPS). A failed save still follows the link. Without JavaScript, or when opening a link in a new tab, the switcher works as an ordinary link without saving a new preference.

For ordinary pages:

- preserve the equivalent path where possible.

For MDX detail pages:

1. identify current entry
2. find sibling using `translationKey`
3. if target translation exists, link to that sibling's stable filename-based URL
4. otherwise link to the corresponding target-locale index

Never display a different-language editorial entry while pretending it belongs to the selected locale.

## HTML metadata

The root layout must set:

```html
<html lang="..."></html>
```

to the active locale.

Also generate alternate-language links for pages that actually have translated equivalents:

```html
<link rel="alternate" hreflang="en" href="..." /> <link rel="alternate" hreflang="cs" href="..." />
```

Do not generate an alternate link to nonexistent content.

## Formatting

For locale-sensitive date/number/currency output, prefer the formatters supplied by the Intlayer ecosystem or `Intl` with the active locale.

Do not hard-code English date formats.
